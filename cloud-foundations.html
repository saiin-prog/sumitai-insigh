What Really Happens Between the CPU and the Cloud

A technical deep dive into how operating systems and virtualization work from the hardware level upward.

Sumit Kumar Jan 11, 2026 · 12 min read

1. Cloud Foundations – Introduction

What really happens between our CPU and the cloud? To understand modern cloud infrastructure, we must first understand how operating systems and virtualization work from the hardware level upward.

This article explains how a CPU executes processes, how memory is virtualized using paging, and how user mode and kernel mode enforce protection and isolation. It extends these concepts to virtualization, demonstrating how hypervisors create virtual machines by multiplexing CPU, memory, and I/O using hardware support such as Intel VT-x and AMD-V.

We also contrast Type-1 and Type-2 hypervisors, explain why cloud platforms rely on bare-metal hypervisors, and outline the performance and security trade-offs involved in running multiple operating systems on the same physical hardware.

2. Process and CPU Execution

What is a Process?

A process is an executing instance of a program. It bundles an address space (code, data, stack), CPU context (registers, Program Counter), OS resources (open files, sockets), and metadata (PID, owner, scheduling priority).

"Virtualization creates virtual processes inside virtualized operating systems. So understanding process structure is necessary to understand how a VM works."

It is important to distinguish a process from a program. A program is a passive file on disk. A process is a running, executing, resource-owning entity created by the OS. The CPU can only execute machine instructions; everything else is just abstractions.

Key Structures and Context Switching

The Process Control Block (PCB) holds critical information: PID, registers, program counter, state, open file descriptors, memory map, parent/children, and credentials.

When the OS switches between processes (Context Switch), it saves the current PCB (registers, PC, other CPU state) and loads the destination PCB. This operation incurs costs from register save/restore, potential TLB flushes, and cache effects.

Why it matters for virtualization: Virtual Machines emulate multiple processes and whole OS instances. Hypervisors must multiplex CPU and memory across guest processes—PCBs inside guests map to guest kernel structures, while the hypervisor maintains per-VM metadata.

3. Virtual Memory and Paging

Virtual memory provides each process with a private, contiguous address space while the operating system and MMU transparently map virtual addresses to physical memory using paging structures.

Virtual vs. Physical Address

Addresses assigned in the memory image used by the CPU to load and store are virtual (logical) addresses. They are not the actual addresses occupied by instructions or data but are assigned from 0 for convenience. The actual addresses where bytes are stored are called physical addresses.

The CPU requests code/data at virtual addresses, which are translated to physical addresses so that RAM can fetch them. Memory is allocated at the granularity of pages (usually 4KB). Logical pages of a process are stored in physical frames in memory, and logical page numbers are translated to physical frame numbers.

Analogy: Office Desk vs. Warehouse

Core Idea: Imagine a worker sitting at a desk in an office. The desk looks large, clean, and continuous, but in reality, the office does not keep everything on the desk at once. Most materials are stored in a warehouse somewhere else.

  • Virtual Memory (The Illusion): To the worker, it keeps one long, continuous desk where everything is neatly laid out. This is virtual memory: the worker sees a clean space, even though real storage is scattered.
  • Pages (Standard Boxes): All materials are stored in same-size boxes (pages) in the warehouse to make movement easy.
  • Page Table (Index Book): An index book allows the worker to know that "Item A is in box 12 on shelf 3". This maps what is on the desk to the warehouse.
  • TLB (Sticky Notes): For frequently used items, the worker keeps sticky notes with quick directions to avoid opening the index book every time.
  • Page Fault: If the worker reaches for something not on the desk or nearby, they must pause and ask support staff to bring it. This pause is a page fault.

4. User Mode and Kernel Mode

Modern CPUs enforce multiple privilege levels to separate application execution from operating system control. This separation is fundamental to system stability, security, and efficient resource management.

Privilege Levels and Rings

  • User Mode (Ring 3 in x86): Applications execute here with a restricted instruction set. Direct access to hardware and privileged CPU instructions is prohibited.
  • Kernel Mode (Ring 0 in x86): The operating system executes here with full privileges, allowing direct access to hardware, protected memory regions, and system-wide resources.

If user code attempts to run privileged instructions, an error is thrown. The privilege level is checked by the CPU and MMU (every page has a privilege bit).

5. Interrupts and Traps

Interrupt and trap handling form a critical control path. When does a process go from user mode to kernel mode?

  • System Call: User requests a privileged action from the OS (e.g., read syscall).
  • Program Fault: Hardware raises a fault when user does an invalid action (e.g., page fault).
  • Interrupt: I/O devices request attention (e.g., packet arrived on NIC).

All these are generally called traps. Upon a trap, the CPU changes privilege level to kernel mode, jumps to OS code that handles the trap, runs it, and then returns to user code (restoring the saved context).


Virtualization Challenges

In virtualized systems, privileged instructions executed by guest kernels may trigger VM exits, transferring control to the hypervisor (trap-and-emulate). Excessive VM exits can degrade performance. Modern hardware support (Intel VT-x, AMD-V) allows guest OSs to run in Ring 0 while efficiently trapping sensitive operations.

6. Hypervisors and Cloud Infrastructure

Type 1 Hypervisor (Bare-Metal)

A Type 1 hypervisor runs directly on physical hardware without an intermediate host operating system. It provides a minimal, high-performance control layer.

  • Core Characteristics: Installed directly on bare-metal; No general-purpose host OS; Designed to isolate multiple VMs; Optimized for performance and security.
  • Use Cases: Enterprise data centers, Public/Private clouds, High-performance workloads.
  • Implementations: VMware ESXi, Microsoft Hyper-V (Server), KVM (Linux-based), Xen, AWS Nitro.

Why Cloud Platforms Use Type 1: Large-scale clouds require near bare-metal performance, strong tenant isolation, and hardware virtualization support. Type 1 hypervisors meet these needs by operating directly on hardware with a reduced attack surface.

Hardware-Assisted Virtualization

Modern CPUs have a special VMX mode. The VMM enters VMX mode to run the guest OS in a special Ring 0, exiting back to the VMM on triggers.

Memory Virtualization

Type 2 Hypervisor (Hosted)

A Type 2 hypervisor runs as an application on top of an existing host operating system. It relies on the host OS for scheduling and drivers.

  • Characteristics: Installed on top of a host OS; Virtual machines run as user-space processes; Optimized for convenience.
  • Use Cases: Local development, testing, learning virtualization.
  • Implementations: Oracle VirtualBox, VMware Workstation, Parallels Desktop.

8. Architectural Summary

Architectural Trade-offs in Cloud Design:

  • Process: The unit of execution. PCB and context switches are fundamental primitives.
  • Virtual Memory: Isolates processes and enables overcommit. Nested paging makes virtualization efficient but adds TLB pressure.
  • User/Kernel Modes: Enforce protection. Hardware virtualization avoids trap-heavy emulation costs.
  • Interrupt/Trap: Kernel handles synchronous/asynchronous events. Virtualization requires clever interrupt virtualization to minimize overhead.
  • I/O: Critical performance path. Architects must choose between emulation, paravirtualization (virtio), or passthrough/SR-IOV.
  • Overall: The trade-off is always Performance ⟷ Isolation ⟷ Flexibility. Cloud-scale efficiency is achieved using paravirtualization and hardware assists.
